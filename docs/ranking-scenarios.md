# ランキング利用シナリオ・統合設計の引き継ぎ

更新日: 2026-08-26

## 1. この文書の位置づけ

ステータスは「要件確定・設計・未実装」。主要なユーザー確認事項はすべて解決済み。既存ランキングと横断ランキングの実装は存在するが、本書の6目的を1つの操作フローへ統合した画面が完成しているという意味ではない。本書は、確定した利用シナリオ・操作・計算要件と、実装への提案をまとめた引き継ぎ文書である。別の作業スレッドでは会話履歴なしで前提を把握し、既存コードとの差を確認して実装に進める。

「確定」はユーザーとの合意、「提案」は実装時の検討材料を示す。過去の確認事項は第8節に解決履歴として残す。現在の試作の挙動や既存コードの初期値を、新設計の確定仕様として自動的に引き継がない。特に、以前の「1ポケモンにつき最良食材構成1件」という案は、この設計では採用しない。

既存機能を土台に統合し、同じ目的の試作機能を独立した別機能として残し続けない方針である。ただし本書は既存ファイルの即時削除、計算処理の全面廃棄、保存データの破棄を指示するものではない。移行範囲は既存実装と照合し、小さな変更で決める。[フォーク境界](fork-customizations.md)と[AGENTS.md](../AGENTS.md)を前提とする。

## 2. 共通の利用フロー（確定）

ランキングは1タブ内の同一フローとする。目的ごとに独立したランキング画面を増設するのではなく、何を比較・探索するかを最初に選び、その目的に必要な条件を順に設定する。

```text
目的を選ぶ
  → 主条件と評価指標を選ぶ
  → 必要なオプションを調整する
  → 計算ボタンを押してランキングを見る
  → 必要なら比較個体を追加する
```

比較個体の追加は「7番目の目的」ではなく、すべてのランキング結果に共通する任意操作である。最初から比較個体の登録を求めない。目的によって必須入力は変わるが、結果の読み方や比較への進み方は共通にする。

6目的の選択にはセレクトを使い、ランキングタブは1つにする。ランキングオプションは初期状態で折り畳み、適用条件の要約を表示する。共有計算環境の既存UIは可能な限りそのまま再利用する。

ランキング計算は計算ボタンで明示的に実行し、条件が変わるたびに全候補を自動再計算しない。条件変更後に古い結果を残す場合は、「条件変更あり／再計算が必要」であることを明示する。計算中の状態と中止操作、失敗理由と再実行手段を用意する。

ランキングが最新なら、比較個体の追加・編集だけはその1個体を自動再評価してよい。共有環境が変わった後は、先に候補ランキングを再計算し、新しい比較値を古い候補値へ混ぜない。結果がどの条件で計算されたかを管理し、表示上も古い結果を最新と誤認させない。

ランキングの主条件・オプションは目的ごとに記憶し、目的切替後に戻ったときもページを再読み込みしたときも復元する。共有計算環境は全目的で共有し、既存保存機能を利用する（第4節）。UI寸法、ファイル分割、進捗表示の具体的な部品などは、上記の操作契約を守る範囲で実装時に決める。

## 3. 6つの目的と主条件（確定）

以下の順序と名前を基準とする。食材構成の固定を主条件の必須入力へ繰り上げず、目的1・3・5・6ではオプションに置く。

| 順序・目的 | 主条件 | ランキング候補として変えるもの | 選べる評価指標 |
| --- | --- | --- | --- |
| 1. ポケモンのサブスキル・性格を比較する | ポケモン1種 | 固定した種・食材構成のサブスキルと性格 | 指定食材獲得量、食材エナジー、きのみエナジー、スキル回数、総エナジー |
| 2. ポケモンの食材構成を比較する | ポケモン1種 | その種の全有効食材構成 | 食材エナジー |
| 3. きのみ要員を探す | きのみ1種 | そのきのみを持つ種 | きのみエナジー、総エナジー |
| 4. 食材要員を探す | 食材1種 | 指定食材を含む種 × 全有効食材構成 | 指定食材獲得量、食材エナジー |
| 5. スキル要員を探す | スキル1種 | そのスキルに該当する種 | スキル回数 |
| 6. 島に合うポケモンを探す | 島 | 島の好きなきのみ3種のいずれかを持つ種 | きのみエナジー、総エナジー |

上表のABC初期値は通常ポケモンについての扱いである。Cを持たない通常ポケモンには既存 `PokemonIv.normalize` のC→A補正を適用するため、ABC指定はABA、AAC指定はAAAとして計算・表示する。全種の初期指定をABAへ変更する意味ではない。

幻の「除外／同食材3枠のみ／全構成」オプションは、探索する目的3〜6だけに適用する。その範囲では通常ポケモンの構成指定より幻専用設定を優先し、通常ABC＋幻の各食材AAA相当を列挙できる。種を指定する目的1では幻も実在する構成1つを固定し、目的2では選んだ幻の全有効構成を比較する。目的1・2へ探索用の幻除外やAAA限定を持ち込まない。

「全有効食材構成」は、その種で成立する構成を比較する意図を示す。目的2・4では最初から有効パターンだけを列挙し、無効なC候補を補正して重複候補を作らない。目的4の指定食材フィルターは候補の実構成の解放済み枠で判定するが、目的2の全構成列挙まで未解放枠を持つ構成を削除する意味ではない。通常の固定構成補正は U-04、食材判定は U-07、幻専用方式は第4節と U-05 を参照する。

### 3.1 ポケモンのサブスキル・性格を比較する

選んだポケモンの種と食材構成を固定し、サブスキル・性格を列挙する。利用者は「この種を、この食材構成で育てるなら、育成条件によってどれほど性能が違うか」を調べる。食材構成オプションの初期値はABCで、AAA・ABBなどへの変更を可能にする。Cを持たない通常ポケモンはフォーク元仕様のC→A補正に従い、例えばABC指定ならABAで計算する。結果にも実際の計算構成を表示し、無効なABC表記を残さない。

幻も直接選択できる。幻を選んだ場合は既存の個体編集UIを使い、実在する食材構成を1つ固定してサブスキル・性格を比較する。探索用の幻専用3段階設定によって、この固定構成を全構成列挙へ切り替えることはしない。

主条件は種であり、毎回食材構成を入力し終えるまで先へ進めない設計ではない。指定食材獲得量を選んだ場合は、評価する食材を選ぶ必要がある。列挙するサブスキルの制約、同値の育成条件の見せ方は、既存実装を調べてから必要最小限で統合する。

### 3.2 ポケモンの食材構成を比較する

種を固定し、性格・サブスキルなどを共通条件にして、その種の全有効食材構成を比較する。性格は無補正、サブスキルはなしを初期値とする。利用者は「同じ育成条件ならどの食材構成がよいか」を見る。評価指標は食材エナジーとし、今回の基本機能として別指標を追加しない。

幻を選んだ場合も、その幻の全有効食材構成を比較する。目的3〜6の幻除外初期値や同食材3枠限定は適用しない。

各構成を個別の候補として残す。種ごとの最良1件へまとめると、この目的そのものが成立しない。構成に含まれる食材名や枠を結果から確認できるようにし、同じ種が複数行に出ることを重複バグと誤解させない。

### 3.3 きのみ要員を探す

きのみ1種を選び、それを持つポケモンを列挙する。候補の性格・サブスキルは共通で、初期値は無補正・なし。食材構成も候補間で固定し、オプション初期値をABCとする。きのみエナジーだけを見るか、総エナジーまで含めるかを選ぶ。

「きのみ要員」は利用目的であり、得意がきのみの種だけに自動限定する意味ではない。今回の主条件として合意したのはきのみ1種である。既存のタイプときのみの対応を利用するが、画面でどの名前・アイコンを出すかは既存UIとの整合を取る。

### 3.4 食材要員を探す

食材1種を選び、その食材を持つ種と全有効食材構成を比較する。例えば同じ種のAAAとABBなどが複数候補として並び得る。性格・サブスキルは共通の固定条件で、初期値は無補正・なし。指定食材の獲得量、または食材エナジーで評価する。指定食材は候補抽出に使うが、食材エナジーを選んだときの順位には、その候補が得る他の食材のエナジーも含める。

この目的は「種を先に無補正で評価して最良構成を1つ選び、その後に育成条件を適用する」処理ではない。比較する各構成へ固定育成条件を適用したうえで性能を計算し、構成を個別に残す。食材フィルターは、指定Lvで解放済みの枠に対象食材が含まれる構成だけを対象とする。種がその食材を持てるだけでは足りない。例えばLv30で第3枠だけに対象食材がある構成は除外し、第1枠・第2枠にあれば残す。フィルターを通過したうえで回収条件等により正常な計算結果が0になる候補は残す。未解放枠による抽出段階の除外と、計算結果0の扱いを混同しない。

### 3.5 スキル要員を探す

スキル1種を選び、その条件に該当する種を列挙してスキル回数を比較する。性格・サブスキル・食材構成は共通の固定条件で、性格は無補正、サブスキルはなし、食材構成はABCを初期値とする。抽出にはフォーク元の `MainSkill.ts` の `matchMainSkillName` を再利用し、同系列派生や関連効果のマッチを含む既存分類に従う。独自の完全一致判定へ置き換えない。

マッチ判定は実際に計算する対象種・個体に対して行い、`evolved` による自動進化で検索範囲を拡張しない。例えばミュウの実個体の選択スキルを無視し、選択可能なすべてのスキルへ無条件にマッチさせる処理は追加しない。既存関数の引数と動作を尊重する。

この目的で「スキルが強い」と表現するときも、今回の評価値は発動回数である。スキル効果量、スキル由来エナジー、チーム全体への貢献を評価しているとは表示しない。

### 3.6 島に合うポケモンを探す

島を選び、その島の好きなきのみ3種のいずれかを持つ種だけを候補にする。「全種を出して好きなきのみ一致分だけ加点する」探索にはしない。評価では好きなきのみ一致を適用し、きのみエナジーまたは総エナジーを比較する。

性格・サブスキル・食材構成は共通固定で、初期値は無補正・なし・ABC。目的6の島・きのみは既存の共有計算設定と同一の値を使い、可変きのみ、エキスパート（EX）、イベント補正のUIと規則を再利用する。その値で確定する好きなきのみ3種に該当する種を候補とする。

島を変更したら共有計算環境を更新し、ランキング候補と比較個体の両方へ反映する。目的別の設定保存があっても、目的6専用の別の島設定を保存して二重管理しない。

## 4. 設定を3区分に分ける（確定）

| 区分 | 主な内容 | 適用先 |
| --- | --- | --- |
| 候補範囲 | 幻を含めるか、進化前を含めるか、目的の主条件による対象抽出 | ランキング候補のみ |
| 候補個体の固定条件 | Lv、スキルLv、リボン、目的に応じた性格・サブスキル・食材構成 | ランキング候補のみ。目的1の列挙軸は固定しない |
| 共有計算環境 | げんき、キャンプチケットなど、性能を計算する環境 | 候補と比較個体の両方 |

LvとスキルLvの固定はすべての目的のオプションに置く。ランキング候補のLv初期値は60、スキルLv初期値はMAXで確定した。MAXは数値8の一律指定ではなく、[MainSkill.ts](../src/util/MainSkill.ts) の `getMaxSkillLevel` が返す各スキルの上限を意味する。現在の戻り値は6・7・8だが、固定数値にせず上限データの更新に追随する。一緒に眠った時間・リボンの初期値は200時間未満、補正なし（`ribbon = 0`）とする。これらの候補初期値を比較個体へ強制しない。

候補のスキルLvを数値へ変更した場合、指定値はスキルレベルアップ（SLU）込みの通常時Lvとして扱う。SLU MがあってもLv5指定なら通常時Lv5で計算し、そこへSLU分を再加算しない。イベント・島等の補正はその通常時Lvへフォーク元の規則で適用し、上限を超える場合は該当スキルの上限までとする。指定値と実効上限の具体的な表示方法は実装裁量とし、計算規則の未決事項にはしない。

候補探索である目的3〜6では、幻を除外し、進化前を除外することを初期値とする。目的1・2の種選択範囲まで同じ初期制限を広げる合意ではない。比較個体は候補範囲の制限に従わないため、進化前や幻であっても、そのことだけを理由に追加を拒否しない。

### 探索目的3〜6の幻専用設定（確定）

「探す」目的3〜6では、幻を通常ポケモンの食材構成指定とは別枠とし、次の3段階を選ぶ。その範囲では通常ポケモンのABC等の固定構成より幻専用設定を優先する。種を指定する目的1・2には適用しない。

- 除外: 幻を候補に含めない。候補探索の初期値は引き続きこれとする。
- 同食材3枠のみ: 同じ食材を3枠すべてに置く有効構成を、各食材について列挙する。1食材だけを選んで固定する意味ではなく、候補数を抑えつつ食材別のパターンを比較する。実データ上、その食材を全3枠に置ける場合だけを候補にする。
- 全構成: その幻の実データで成立する全食材構成を列挙する。通常ポケモン側のABC指定などでこの列挙を制限しない。

例えば「通常ポケモンはABC、幻は同食材3枠のみ」なら、通常の種はABC（C未所持ならABA）、幻は各食材のAAA相当を候補にする。目的4の指定食材フィルターは幻にも適用し、専用設定を選んだことを理由に無条件で全幻構成を混ぜない。幻も通常ポケモンと同様に、指定Lvで解放済みの枠に対象食材があるかで判定する。比較個体は、この幻専用の候補生成設定にも従わせない。

### 共有計算環境と既存UI

共有するのは計算環境だけである。既存の詳細設定オブジェクトにはLvの一括変更や進化後換算など個体を書き換える項目も含まれるため、そのオブジェクト全体を無条件に「共有環境」と見なさない。入力上の区分と実際の計算への渡し方を一致させる必要がある。

フォーク元の詳細設定UI、個体編集UI、ボックス、保存データは可能な限り再利用・保持する。既存のパネルと同じ設定を持つ「新しい共通設定パネル」を重複して実装しない。既存部品を組み合わせ、個体固定オプションと環境項目の境界を整理する方針とする。

### 設定の保存とリセット（確定）

ランキングの主条件・オプションを目的ごとに保存し、目的切替からの復帰とページ再読み込み後に復元する。共有計算環境は既存の保存機能で全目的に共有する。島など主条件と環境にまたがる同一項目は二重管理せず、目的別設定の保存を理由に別の環境値を作らない。

ランキング設定のリセットは現在の目的だけを対象にする。共有計算環境、他目的のランキング設定、ボックスを変更しない。保存キーや型の具体設計は既存形式を確認して実装するが、この保持単位・復元範囲・リセット範囲は確定事項である。

## 5. 比較個体の独立性（確定）

比較個体は、ランキングの条件に合わせて複製・変形した候補ではない。種、食材構成、Lv、スキルLv、性格、サブスキル、リボンのすべてを、その比較個体自身の自由な値として持つ。候補の固定Lv、固定構成、主条件、範囲フィルターなどで上書きしない。この点は、候補と比較個体の育成条件まで揃える案ではなく、「げんき・キャンチケ等の環境のみ共有する」という最終合意に従う。

結果へ追加した比較個体は、その個体の値と共有計算環境を使い、現在選択中の評価指標で計算する。ランキングがげきからハーブ獲得量なら比較個体も同じ食材の獲得量で評価するが、比較個体の食材構成をげきからハーブ入りへ変更することはしない。正常に計算できて値が0になる場合は0として扱う。比較個体が計算不能なら表示から消さず、計算不可の理由を示して順位は付けない。

既存の手動編集や登録済み個体を利用することを優先する。比較個体はまず1個体とし、結果へ追加して位置を強調し、その順位へ移動できるようにする。同値時の比較挿入や相当順位などの実装詳細は既存の比較処理を踏襲する。比較を追加しても、目的2・4の同順位食材構成を候補から落とさない。

### 利用シナリオ例

- カイリューの食材構成を指定し、サブスキル・性格のランキングを生成する。その結果へ手持ちのAAAゲンガーを比較個体として追加し、げきからハーブ獲得量がどの位置にあるかを見る。カイリュー側の種・構成・固定Lv等を、ゲンガーへコピーしない。
- AAAミカルゲのサブスキル・性格ランキングを生成する。その結果へ手持ちのABBゲンガーを比較個体として追加し、あじわいキノコ獲得量がどの位置にあるかを見る。比較するゲンガーは自身の種・ABB構成・Lv等を維持する。

これらは操作とデータの独立性を説明する例であり、どの種・構成が「最強」かを断定するものではない。実際の優劣は入力された個体条件、計算環境、評価指標に依存する。

## 6. 評価指標の範囲と意味

今回の指標は第3節の目的別一覧で確定している。調査中に挙がった総食材数、スキルエナジー、RP、スキル効果量は今回追加しない。既存・試作のAPIやUIに総食材数などがあっても、それだけで統合画面へ採用する理由にはならない。

指定食材獲得量は、既存仕様と同様に通常のおてつだいで得る指定食材だけの獲得量を扱い、スキル由来の獲得分は含まない。「食材エナジー」は、目的1・2・4すべてで通常のおてつだいから得る全食材の合計エナジーと確定した。選択した食材分だけのエナジーではない。料理・レシピ等の補正も既存の `PokemonStrength` 計算を使い、別計算を新設しない。この定義を説明とテストにも反映する。

目的4では「指定食材で対象を絞ること」と「全食材の合計エナジーで順位を付けること」を区別する。指定食材獲得量へ切り替えた場合だけ、その食材の獲得量で順位を付ける。U-01はこの内容で解決済みである。

きのみエナジー、総エナジー、スキル回数は既存計算結果の再利用を基本案とする。計算期間や補正は共有環境と整合させ、単位と期間を結果から確認できるようにする。スキル回数をスキル効果量として表示しない。

総エナジーは既存の `totalFlags` と `addHelpingBonusEffect` の設定を尊重する。設定により、おてつだいボーナスによる他4体への寄与なども含み得るため、常に「本人だけのエナジー」とは限らない。この選択を新しい独自設定で置き換えず、既存計算環境を再利用する。

### 順位とページング（確定）

丸め前の計算値が完全に等しい候補を同順位とし、順位は1・1・2となるdense方式を採用する。表示用の丸めを順位判定へ流用しない。1ページは100順位グループ単位とし、同順位に別の食材構成や個体条件があっても確認できるようにする。目的2・4では同順位の構成も独立した候補として残す。

同値内順序、比較挿入、件数表記などの実装詳細は既存のランキング・比較処理を踏襲する。今回の目的別指標以外に新しいソート軸を追加しない。比較個体の強調・順位移動と併せ、U-10・U-11はこの方針で解決済みである。

### 計算不能と0値（確定）

データ不足や固定性格と非互換のフォーム等で計算できない候補はランキングから除外し、除外件数と理由を確認できるようにする。正常に計算できた0値の候補は残す。目的4で対象食材が未解放枠だけにある構成は、計算結果が0だからではなく、事前の食材フィルターで対象外になる。

比較個体は候補の除外一覧へ移して消すのではなく、入力した個体を残したまま計算不可理由と順位なしの状態を表示する。計算不能の具体的な検出・理由分類は既存データと計算処理を調べて実装するが、除外／保持の規則自体は確定事項である。

### 食材名の表示（確定した追加要件・未実装）

ランキングの食材名は『Pokémon Sleep』の正式名へ統一する。現在の [日本語データ翻訳](../src/i18n/ja/data.json) の `ingredients` には19食材の正式名がある一方、[フォーク日本語翻訳](../src/fork/i18n/ja.json) の `ingredient names` には「キノコ」「りんご」「ハーブ」等の略称がある。表示は既存の `ingredients.<key>` を再利用し、例えば「あじわいキノコ」「とくせんリンゴ」「げきからハーブ」とする。新しい正式名一覧をフォーク側へ二重管理しない。

この変更は表示名の整合であり、`mushroom`、`apple`、`herb` 等のデータキーや保存形式を変える要件ではない。他言語も既存の食材翻訳を再利用し、選択肢・結果・説明で一貫した名称を表示する。対象は既存 `IngredientRankingView.tsx` と `CrossPokemonRankingView.tsx` の独自 `ingredient names` 参照を含む。アプリコードはまだ変更していない。

日本語の19名称は、既存共通翻訳と[攻略・検証Wikiの食材一覧](https://wikiwiki.jp/poke_sleep/食材/食材の一覧)が全件一致していることを確認した。公式発表でも、[げきからハーブ・あじわいキノコ等](https://www.pokemonsleep.net/news/343233393938313932383936343432333832/)、[とくせんリンゴ・リラックスカカオ・めざましコーヒー](https://www.pokemonsleep.net/news/323239343336313633313732303733343733/)、[つやつやアボカド](https://www.pokemonsleep.net/news/333234393736353333383231313934323431/)、[ほっこりポテト・ワカクサコーン・ずっしりカボチャ等](https://www.pokemonsleep.net/news/333838303833383530323932343934333337/)を照合した。全19名称を公式ページだけで確認したという主張ではなく、公式発表・補助資料・既存翻訳の照合に基づく。対応表は末尾付録を参照。

## 7. 既存コードとの接続と共通化案（提案）

実装に使える既存の入口を以下に示す。現時点の名称・責務の参照であり、そのまま新仕様を満たすという保証ではない。

| 参照先 | 調査・再利用する部分 |
| --- | --- |
| [RankingWorkspace.tsx](../src/fork/RankingWorkspace.tsx) | 画面の合成、既存IV state・ボックス・詳細設定への接続 |
| [IngredientRankingView.tsx](../src/fork/IngredientRankingView.tsx) | 既存の育成条件比較、比較個体、結果・同値表示 |
| [CrossPokemonRankingView.tsx](../src/fork/CrossPokemonRankingView.tsx) | 横断候補の入力・結果表示、保持する設定の入口 |

| [PokemonRanking.ts](../src/util/PokemonRanking.ts) | `calculatePokemonRankingAsync`、食材構成を含む横断候補と評価結果 |

| [IvForm.tsx](../src/ui/IvCalc/IvForm/IvForm.tsx)、[StrengthParameterForm.tsx](../src/ui/IvCalc/Strength/StrengthParameterForm.tsx) | 個体編集と詳細設定の再利用。新規の重複フォームを避ける |

共通化の基本案は、目的ごとの候補生成だけを分け、完成した個体を評価する後段を共有することである。

```text
目的・主条件・候補範囲・候補固定条件
  → 目的別の候補生成
  → 各候補の性能計算 ← 共有計算環境
  → 選択指標の取得
  → ソート・結果表示
                  ↑
       比較個体を独立に計算して追加
```

候補生成は、種・構成・性格・サブスキルのどれを固定／列挙するかを明示する関数群で十分と考える。小さな型と関数で責務を表し、任意の軸を組み合わせる汎用ランキングフレームワークや大きなクラス階層を先に作らない。候補の識別子は種だけでなくフォームと食材構成などを含め、複数構成を消さない。

評価では個体と共有環境を別の入力として渡す。順位判定の共通処理を再利用できても、候補抽出条件を比較個体の評価に再適用しない。キャンセル、計算不能の扱い、安定した結果順など既存の仕組みも確認する。API名や型の最終形、どこまで既存関数を抽出するかは提案段階である。

実装上の注意として、旧詳細設定の `level`、`evolved`、`maxSkillLevel` を個体条件とは別に扱う必要がある。候補や比較個体を計算時に別Lv・進化後の種へ変えず、比較個体のスキルLvを旧 `maxSkillLevel` によってMAXへ上書きしない。候補の固定スキルLv指定もSLUを二重加算せず、その後のイベント・島補正と上限適用だけを既存計算へ接続する。これは新たな自由度を設ける提案ではなく、確定した個体条件の独立性を既存APIで守るための確認点である。

画面は既存を統合するが、フォーク専用UI・翻訳は `src/fork/`、計算処理は `src/util/` に置く境界を維持する。既存 `src/ui/` へのランキング専用分岐追加は避ける。既存APIの挙動をテストで押さえてから内部を分離し、新しい目的を順に接続する進め方を推奨する。保存キーや形式の移行が必要なら、その範囲を別途明示する。

## 9. 受け入れ条件

確定要件を満たしたことを、次の観点で検証する。

1. 1つのランキングタブのセレクトに指定の6目的が指定順で提示され、主条件、候補軸、評価指標が第3節と一致する。比較個体は独立した目的になっていない。オプションは初期折畳みで適用条件要約が見える。
2. 目的1は幻も含め種・1構成固定で育成条件を列挙し、目的2は選んだ種の全有効構成を比較する。目的2・4は構成を最良1件へ集約しない。目的3・5・6は通常ポケモンの構成を共通固定して種を列挙し、目的3〜6の幻には専用構成設定を優先する。目的1・2に探索用の幻制限を適用しない。
3. ABC固定は通常ポケモンの該当目的のオプション初期値として扱われ、C未所持ならC→A補正後の実構成を計算・表示する。目的2〜6の性格無補正・サブスキルなし、目的3〜6の幻・進化前除外、全目的の候補Lv60・スキルLv MAX・リボン補正なし（200時間未満）が初期状態に反映される。MAXはスキルごとの上限を使う。
4. 島探索は既存共有環境から確定する好きなきのみ3種に該当する種だけを抽出し、計算にも好きなきのみ一致を適用する。島変更を共有環境と比較個体にも反映し、別島設定を二重保存しない。条件なしの全種総当たりを基本機能として追加しない。
5. 比較個体の7つの個体条件が候補条件によって変化しない。異なる種、異なる構成、異なるLvの比較でも共有環境だけを揃えられる。旧 `level`・`evolved`・`maxSkillLevel` による暗黙の上書きを防ぐ。
6. 指定食材獲得量にスキル由来を混入させない。食材エナジーは目的1・2・4で通常のおてつだいの全食材合計とし、既存計算の補正を使う。目的4でも指定食材以外の分を含める。未採用の総食材数・スキルエナジー・RP・スキル効果量を今回の選択肢へ増やさない。
7. 既存ボックス、個体編集、詳細設定の保存データが保持され、重複した設定パネルが生じない。主条件・オプションは目的ごとに切替復帰・再読み込み後まで保持する。現在目的のリセットが共有環境・他目的・ボックスを変えないことを検証する。
8. 目的4の食材抽出は指定Lvの解放済み枠で判定し、目的2の全構成列挙まで制限しない。C未所持の固定構成補正と全構成列挙時の重複防止をテストする。計算不能候補は件数・理由付きで除外し、正常な0値候補は保持する。計算不能な比較個体は消さず、理由・順位なしを表示する。
9. フォーク境界と5言語のキー整合を守り、狭いテストから全体検証へ進む。完了時に `npm run verify` を実行し、タスクに属する変更だけをコミットする。
10. 食材名は既存の `ingredients.<key>` を使って正式名を表示し、データキー・保存データは変更しない。
11. 探索目的3〜6の幻専用設定を3段階で区別し、同食材3枠のみでは実データ上全3枠で可能な各食材を列挙する。通常ABCと幻AAA相当が共存し、目的4の食材フィルターが幻にも適用される。
12. 数値スキルLv固定はSLU込みとして計算し、二重加算しない。イベント・島補正およびスキル上限は既存計算へ従う。目的5の抽出も既存 `matchMainSkillName` 分類を再利用する。
13. 丸め前の完全同値をdense順位で扱い、100順位グループ単位でページングする。同順位構成・個体条件を確認でき、比較1個体の位置強調・順位移動ができる。既存比較挿入処理を踏襲し、目的2・4の同順位構成を保持する。
14. 条件変更だけでは全候補を自動計算せず、計算ボタンで実行する。古い結果の未更新表示、計算中状態、中止、失敗理由・再実行を確認する。最新ランキングへの比較追加・編集は単体再評価し、共有環境変更後は候補を先に再計算して古い値と混ぜない。中止・条件変更・再実行の後、遅れて完了した旧計算が最新結果を上書きしない。

## 10. 別スレッドで再開する際の確認手順

まず本書が実装済み仕様の説明ではないことを確認する。次に実作業時点の差分・コミットを調べ、第7節の入口と関連テストを読み、既存と新要件の差を短く列挙する。新しい画面を作り始める前に、既存UI・保存形式のどこをそのまま使えるかを明らかにする。

U-01〜U-13はすべて解決済みの確定規則として扱い、質問をやり直さない。計算APIの接続方法、保存キー、UI寸法、内部ファイル分割、進捗表示の部品等の技術的選択は実装裁量とし、開発を止める未決事項へ拡大しない。既存挙動との衝突が見つかり、確定した意味を変える必要がある場合だけ、具体的な根拠とともにユーザーへ確認する。

その後、候補生成・比較評価・共通環境・結果表示に分けた小さな実装計画を提示する。既存出力を保護するテスト、目的別の列挙テスト、候補条件から独立した比較個体テストを先に整える案を推奨する。結果の計算条件と編集中条件の一致も検証し、古い結果の誤表示を防ぐ。実装・検証・調整を小さく繰り返し、受け入れ条件の未達を残したまま完成扱いにしない。
